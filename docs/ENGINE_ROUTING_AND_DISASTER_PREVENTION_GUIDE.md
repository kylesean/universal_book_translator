## 0. 一分钟直面困惑：为什么 In-Place 在长篇论文上翻车了？

在之前的讨论中，我们建议并重构了 **In-Place（项目内代号 `rigid`）** 原位几何覆写引擎（利用 pikepdf 剥离原文字流，在源页底板像素级回填译文）。  
然而，当你在 92 页的学术论文（如 DeepSeek 最新论文）上强开 `--render-engine rigid --preset fast` 时，却看到了：**标题贴左、作者角标叠字、摘要末尾腰斩截断、目录全英文未翻、译文粗糙**。

这并非偶然 Bug，而是**原位覆写（In-Place）机制在长篇学术流式排版场景下的“信息论物理死穴”**：
1. **中英文本长度不守恒**：原文作者为英文精心微调了一个高度固定的矩形框（例如摘要高 256 pt）。翻译成中文后，行距与字号无法在保持美观的同时恰好填满该框。一旦中文垂直溢出，为了防止覆盖下方的图表和正文分割线，原位引擎的安全机制必须**硬截断（Truncation）**，导致末句直接丢失。
2. **几何框不等于排版语义**：PDF 文本层只存有每个单词的绝对坐标（BBox），丢失了原始 LaTeX 的居中对齐、首行缩进等语义。原位引擎只能在一个方框内执行默认左对齐，大标题自然向左贴边。
3. **上标图元被坐标粉碎**：作者名后面的角标 `1,2` 在 PDF 中是独立微小字形。粗暴合并后塞回扁窄的框内，中文排版折行必然和下方的机构名叠字撞车。
4. **排版杂质漏采导致底板残留**：目录是由点阵前导线（`1. Introduction . . . . 4`）组成的。文档解析器将其识别为非文本排版杂质而跳过。原位引擎**“没采到的块就不剥离原底板”**，导致整页英文目录原封不动留在成品上。

**结论**：**In-Place（`rigid`）与从零重排（`reflow` / `publication`）是为两类完全不同的物理文档形态量身定制的武器，强行错配必然导致灾难。**

> **与当前 `auto` 调度的对齐说明（2026-09-25）**：本节是**强制指定** rigid 的错配复盘，不等于"学术论文一律 reflow"。当前 `auto` 的判据是**结构密度 + 几何可用性**（含公式、或公式/表格/图/代码块占比 ≥20% 且有可信几何 → `rigid`；纯正文 → `reflow`；无几何兜底 → `reflow`），见 §2——这一调度背后是 reflow 在图表密集论文上的实测丢图证据（arXiv 2609.20519：6 图丢 4）。rigid 的截断缺陷此后也已由**自适应缩字号**（下限 `min_font_pt`，见 §1.2）缓解。本案真正的教训是**"不知情的强制错配"**：拿不准永远留 `auto`。

## 1. UBT 核心引擎全景矩阵

UBT 的处理管线分为两层：**提取层（Parser Engine）** 与 **渲染层（Render Engine）**。

```
┌───────────────────────────────────────────────────────────────────────────┐
│                           UBT 双层引擎拓扑                                │
├───────────────────────────────────────────────────────────────────────────┤
│ [输入源] ──► [提取层 Parser] ──► [中间语义表示 IR] ──► [渲染层 Renderer]  │
│                                                                           │
│   PDF/EPUB     1. docling (重型结构化)               1. reflow /          │
│                2. pdfium  (轻量纯几何)                  publication       │
│                3. auto    (启发式自适应)                (Typst 弹性重排)  │
│                                                      2. rigid (In-Place)  │
│                                                         (pikepdf 底板原位)│
│                                                      3. auto (自适应路由) │
└───────────────────────────────────────────────────────────────────────────┘
```

### 1.1 提取层引擎（Parser Engines）

| 引擎名称 | 依赖与环境 | 核心机制 | 最佳适配场景 | 致命缺陷 |
| :--- | :--- | :--- | :--- | :--- |
| **`docling`** | PyTorch / 模型依赖 (~2GB) | 版面分析模型 (LayoutFormer) + 表格结构模型 + 公式 VLM 检测 | 复杂多栏论文、带表头表格、复杂数学文献 | 启动慢（单核 CPU 耗时数秒），纯纯文本偏重 |
| **`pdfium`** | 仅 `pypdfium2` (轻量 C++ 绑定) | 直接读取 PDF 内部文字流字符矩形，执行双栏聚类与段落重组 | 原生数字单/双栏书籍、无复杂公式的快速扫描 | 无法识别图片内文字、无法提取扫描件、无法重构复杂表格结构 |
| **`auto`** | 动态按需加载 | 采样文档前/中/后页面：含扫描/复杂公式切 `docling`，纯净单栏切 `pdfium` | **默认推荐**：通用文档 | — |

### 1.2 渲染层引擎（Render Engines）

| 引擎名称 | 原理与底层 | 核心优势 | 致命代价 | 最佳适配场景 |
| :--- | :--- | :--- | :--- | :--- |
| **`reflow`**<br>*(别名 `publication`)* | 基于 IR 语义树，使用 **Typst 现代化排版编译器从零生成新版面** | 1. **弹性流动**：文字变长自动推挤分页，永不丢字截断<br>2. **规范美感**：标题自动居中，字阶字偶距符合出版标准<br>3. **语义重排**：按 IR 语义树重排章节标题与段落（PDF 大纲/书签尚未生成，见 `docs/PDF_SKILL_BORROWINGS.md`）<br>4. **双语对齐**：完美支持 `facing`（左右镜像）、`inline`（段落交替） | 若原文包含极其复杂的非标准矢量拓扑图，需依赖解析器的局部切图见证 | **正文主导、结构抽取可靠的文档**：小说、人文社科、纯文本教材、结构可靠的双语出版物（图表密集型见 `rigid`） |
| **`rigid`**<br>*(即 In-Place 几何覆写)* | **源 PDF 为透明画布底板**，使用 pikepdf 剥离原文字流，在原有 BBox 坐标上叠印 Typst 缩字文本框 | 1. **像素级保真**：非文字区域（背景插图、几何图形、表格网格）100% 逐像素不变<br>2. **生成极速**：单阶段批量 Typst 编译 + 页面合并 | 1. **空间约束**：译文变长先自适应缩字号（下限 `min_font_pt`），仍放不下才被 `clip:true` 截断；变短留白<br>2. **排版失真**：丢失居中语义，全贴左对齐；容易叠字<br>3. **不支持双语**：单张底板无法放下两份语言，强开必降级单语 | **公式/图表/结构密集的学术论文与技术文档**（auto 会主动选它）、PPT 幻灯片、单页宣传海报、工业产品单页说明、极度依赖原背景网格的表单 |
| **`auto`** | 结构密度 + 几何可用性判据（`adaptive_policy.resolve_render_engine_from_signals`，单一权威） | 无公式且公式/表格/图/代码块占比 <20% 的纯正文走 `reflow` 拿更好版式；含公式、或该占比 ≥20% 且有可信几何走 `rigid` 保真；全篇无可信几何（纯文本兜底提取）强制回 `reflow` | — | **绝大多数场景的最佳首选** |

## 2. 智能路由决策系统（How Auto-Routing Works）

很多用户误以为必须手动传入 `--render-engine` 或 `--preset` 才能工作。实际上，UBT 内置了严谨的多阶段探测器，**不带参数使用 `auto` 才是最安全的**：

```
                             用户输入文档
                                  │
                   ┌──────────────┴──────────────┐
              是否为 PDF?                      EPUB / MD / DOCX
                   │                                     │
           [engine_selector 探测]                 进入各自原生流式排版
                   │
    ┌──────────────┴──────────────┐
  文字层是否存在？                 
    ├── 否 (纯图/扫描件) ──► 强制路由至 Docling + OCR 识别
    └── 是 (原生数字 PDF)
          │
      抽样页面分析 (前、中、后 3-5 页)
          ├── 右栏边缘占比 PROBE_COLUMN_SHARE 判定：单栏 vs 多栏
          └── 公式碎片密度 PROBE_FORMULA_SHARE 判定
          │
          ▼  （以上探针只决定**解析层**选 docling 还是 pdfium）
  [adaptive_policy 决断渲染层]（auto 的真实判据：结构密度 + 几何可用性，与页数无关）
    ├── 全篇无可信几何（解析落到纯文本兜底）──► publication/reflow（零面积 bbox 必须重排）
    ├── 含数学公式 或 公式/表格/图/代码块占比 ≥20% ─► rigid（保背景几何，图表零丢失）
    └── 纯正文（无公式且结构占比 <20%）──────► publication/reflow（弹性分页 + 更美版式）
```

## 3. 六大经典参数灾难矩阵（Misconfiguration Disaster Matrix）

如果手动强行指定了互相矛盾或不适合文档形态的参数，流水线将不可避免地产生严重缺陷：

### 灾难 1：对长篇学术论文强开 `--render-engine rigid`（本次翻车案情）
* **错误原因**：92 页论文充满复杂标题、带角标作者、长摘要、连续双栏正文与公式。强行命令系统使用原位白框覆盖。
* **交付后果**：
  * 摘要垂直高度不够，末句被强制 Truncate 截断丢弃；
  * 作者角标折行，与下方机构名文字发生重叠（Overlap）；
  * 目录点线未被捕获，全英文底板泄漏。
* **正确解法**：去掉 `--render-engine rigid`，改用 `--render-engine reflow`（正文主导、或需要双语对照时）；图表/公式密集、纯单语交付的论文则**留 `auto`**——它会自行调度到 rigid 并依托缩字号与见证机制控制上述缺陷。本案例的价值在"强制且不知情"的代价。

### 灾难 2：对严谨专著强开 `--preset fast`
* **错误原因**：`fast` 预设是针对“5 分钟扫读论文大意”设计的极速预设，它在 `ubt/core/presets.py` 中只改质量参数（从不关闭任何正确性门禁）：
  1. `exec_mode="short"`——**强制走短链**（路由器中 short 强制生效，不分篇幅），术语圣经退化为 fast-lane seed（不整书提炼与强制统一专有名词）；
  2. `prompt_strategy="minimal"`——最小提示词，不携带全书上下文；
  3. `formula_enrichment="off"` + `formula_render="image"`——公式跳过重新识别，直接用源图切片；
  4. 零重型依赖、轻量几何抽取，短链极速执行。
* **交付后果**：seed-only 圣经造成术语前后矛盾，最小提示词带来机翻味与漏译，公式不重新识别——译文粗糙不可交付；长篇专著也被整本塞进短链语境。
* **正确解法**：正式交付使用 `--preset publication`（全功能术语对齐 + 两轮修复）或 `--preset standard`。

### 灾难 3：追求双语对照，同时强行指定 `--render-engine rigid`
* **错误原因**：原位覆写（In-Place）的底层只有一张原始单页底板，没有物理空间并排展示两种语言。
* **交付后果**：流水线会发出警告并将双语模式强制降级为单语（Monolingual）。
* **正确解法**：只要需要双语对照（`--dual-mode facing` 或 `inline`），必须使用 `--render-engine reflow`。

### 灾难 4：对纯图片扫描件强开 `--ocr off`
* **错误原因**：文档完全没有可提取的矢量文本层，却强行关闭了 OCR 驱动。
* **交付后果**：解析器提取出 0 个 Block，系统直接触发“拒绝空书（Reject Empty Book）”或输出全白 PDF。
* **正确解法**：扫描件必须保持 `--ocr auto` 或显式启用 `--ocr sidecar` / `--ocr cloud`。

### 灾难 5：切片抽检（`--pages 1-5`）误触发全局语言密度拦截
* **错误原因**：整本 92 页只翻译了 5 页，其余 87 页全是英文。以前物理见证门禁在计算中文占比时按整书统计，导致中文仅占 0.88% 被拦截。
* **现状与修复**：在 Commit `9779f44` 中，已升级为切片感知检验（只检验所选 5 页），该问题已完全攻克。

### 灾难 6：输出路径指定为目录或无后缀（如 `--output ./out_fast`）
* **错误原因**：CLI 习惯将 `--output` 作为目录传递，而 Typst 编译器必须依赖明确的 `.pdf` 后缀推断格式。
* **现状与修复**：在 Commit `9779f44` 中，新增了 `resolve_target_output`，系统自动补齐 `.pdf` 或拼合规范文件名，彻底解决格式推断报错。

## 4. 场景化最佳实践速查手册（User Playbook）

为了获得最好的可交付质量，推荐针对不同业务场景采用以下黄金组合：

### 场景 A：学术论文 / 专著 / 长篇技术手册（如 92 页 DeepSeek 论文）
> **核心诉求**：文字完整、标题严谨、目录正确、无截断、出版级印刷质量。

```bash
# 推荐：保持 auto，让结构密度决定路线（公式/图表密集 → rigid 保真，纯正文 → reflow）
uv run ubt translate input_paper.pdf \
  --preset publication \
  --render-engine auto \
  --output ./deliverable.pdf

# 确认结构抽取可靠、需要面对面双语对照时，显式走 reflow
uv run ubt translate input_paper.pdf \
  --preset publication \
  --render-engine reflow \
  --dual-mode facing \
  --output ./deliverable_bilingual.pdf
```

### 场景 B：排版严重依赖原背景的单页海报 / PPT / 工业制图单页
> **核心诉求**：背景底图 100% 逐像素不变、矢量框格原样留存、文字极少。

```bash
uv run ubt translate single_slide.pdf \
  --render-engine rigid \
  --output ./slide_zh.pdf
```

### 场景 C：极速扫读 / 确认核心结论（低开销）
> **核心诉求**：几秒钟看个大意，对排版对齐和术语润色不做严苛要求。

```bash
uv run ubt translate input.pdf \
  --preset fast \
  --pages 1-3 \
  --output ./quick_look.pdf
```

### 场景 D：纯正文小说 / 电子书（EPUB / Markdown）
> **核心诉求**：流式重排、段落章节自适应。

```bash
uv run ubt translate novel.epub \
  --preset standard \
  --dual-mode inline \
  --output ./novel_zh.epub
```

## 5. 架构师给出的最终选型心法

> **“流式文本选 Reflow，固定几何选 Rigid，拿不准永远留 Auto。”**
>
> 1. 不要把 In-place（`rigid`）当做长篇学术图书的万能银弹。全世界所有声称实现“1:1 完美原位翻译”的工具，在面对跨段文字长度变化时，要么在截断文字，要么在强行缩小字号变成看不清的“蚂蚁字”。
> 2. 出版级翻译的尊严在于**“文字不丢、层级分明、排版舒展”**。Typst 的重排流水线（`reflow`）才是承载大部头文献真正交付质量的护城河。
